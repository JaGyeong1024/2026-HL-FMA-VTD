## 1. 이번 세션에서 한 것

### 1-1. 플래너 SIGABRT 크래시 (`a1b4015`)

**증상**: `behavior_planning` 컨테이너가 주행 중 죽고 `/planning/trajectory` 가 끊겨
차가 그 자리에 정지. 최근 14회 주행 중 **8회** 발생. NG·JG 모두 겪던
"될 때 있고 안 될 때 있다"의 정체.

```
terminate called after throwing an instance of 'std::invalid_argument'
  what():  query_keys is out of base_keys
process has died [exit code -6]   ← SIGABRT
```

**원인 사슬** (전부 코드로 추적):
```
calc_shift_intervals 가 빈 배열 반환 (그 방향에 차선변경 구간 없음)
  → lane_changing_length = DBL_MAX,  current_dist_buffer = 0
  → next_dist_buffer.min = 0 - DBL_MAX - 2.0 = -DBL_MAX
  → get_reference_path_from_target_lane 의
      s_end = min(..., target_lane_length - (-DBL_MAX)) = +inf
    → 길이 검사(s_end - s_start < lane_changing_length)를 무력화하고 통과
    → getCenterLinePath 는 s_end 를 대상 차로 실제 길이로 잘라냄
    → resamplePathWithSpline 의 보존 키가 경로 밖 → throw → SIGABRT
```

**수정 3겹**:
1. `s_end` 를 대상 차로 실제 길이로 한 번 더 클램프 — 근본 수정
2. 기준경로 생성 예외를 후보 단위로 처리 (프로세스 종료 대신 후보 폐기)
3. ~~오염된 `lane_changing_length` 면 후보 생성 조기 차단~~ → **철회** (`460cd69`)
   우회는 목표가 선호 차로 방향이 아니라 `DBL_MAX` 가 **정상 상태**였다.
   이걸 막았더니 우회 후보가 14회 전부 차단돼 회피를 못 했다.

**잔여 예외 처리** (`dddd976`): 길이 검사가 호 좌표 추정치라
`getCenterLinePath` 의 실제 반환 길이와 어긋나 16회가 더 났다. 실제 길이로 재검사해 0회.

### 1-2. 주행가능영역 (`f697e37`, `dddd976`, `eb91bc9`)

**질문**: "장애물도 없는데 왜 주행가능영역이 줄어드나"

**답**: Autoware 의 주행가능영역은 **장애물과 무관**하다. `generateDrivableLanes()` 가
`current_lanes + target_lanes` 로만 만든다. "갈 수 있는 곳"이 아니라
**"지금 모듈이 쓰겠다고 선언한 차선"** 이고, MPT 최적화기의 제약조건이다.

**전수 조사 결과, 노선(선호 차로)을 무조건 영역에 넣는 코드가 어디에도 없었다.**
기본 영역은 `getLaneletsFromPath(reference_path)` — 지금 경로가 지나는 차선뿐이다.

**수정**: `getReferencePath` 와 `lane_change` 의 `generateDrivableLanes` 양쪽에서
노선에 속한 좌/우 이웃 차로까지 같은 entry 를 넓혔다.
entry 를 추가하지 않고 넓히기만 해 종방향 순서와 순환 판정에 영향이 없다.

`lane_change` 쪽에도 넣어야 했던 이유: `combineDrivableAreaInfo` 는 이름과 달리
**합집합이 아니다**. 결과의 길이·순서를 첫 인자(모듈 자기 선언)가 정하므로,
차선추종 단계에서만 넓히면 차선변경 모듈 승인 중에는 그 2차로 선언이 골격이 된다.

**결과**: 앞쪽 폭 3.2 m → 16 m 유지.

### 1-3. 차선변경 완료 판정 교착 (`8fbb078` — B)

**증상**: 정지 후 2200 사이클 전부 `lane_change_left RUNNING → RUNNING`.
초록불이 여러 번 지나가도 재출발 못 함.

**원인**: `hasFinishedLaneChange` 는 종료점을 못 지나면
**횡오차 0.1 m + 요오차 1.0°** 를 요구한다. 실측 정지 상태 값:
```
dist_to_end=12.6m  yaw=31.2°(임계 1.0°)  lat=-1.95m(임계 0.1m)  v=0.00
```
정지 상태라 자세가 개선될 수 없어 **영구 교착**. 모듈이 안 끝나니 종점 정지점도 계속 꽂힌다.

**수정**: 종료점을 못 지났어도 **자차 footprint 가 목표 차로에 온전히 들어왔고
요 편차가 크지 않으면 완료**로 본다. footprint 포함은 중심점 포함보다 엄격해
두 차로에 걸친 상태를 완료로 오판하지 않는다.

**효과 확인**: `lane_change_left` 가 t=71.2 에 승인 목록에서 빠졌다(이전엔 끝까지 남음).
누적 220 → 778 m.

### 1-5. 불완전 출력 유지 (`7fbab0e` — PM_HOLD)

**증상**: 경로가 307 m ↔ 20~45 m 로 왕복 (9회).

**원인**: 기준경로는 successor 만 따라가므로 **노선이 차선변경을 요구하는 지점에서 끊긴다**
(예: 14633 → 14611 은 successor 가 아니라 차선변경). 차선변경 모듈이 그 사이클에
경로를 못 채우면 그 토막이 그대로 발행된다. 노선 위에 있지만 불완전한 경로다.

**수정 위치가 중요했다**: 처음엔 `generateOutput()` 안에 넣었는데 **0회 발동**했다.
토막이 나오는 사이클엔 모듈이 선택되지 않아 그 함수 자체가 호출되지 않기 때문이다.
`planner_manager` 의 **최종 출력 직전**으로 옮기니 13회 발동했다.

조건: 직전 출력의 **절반 미만**으로 줄고, 보관본이 **1.5초 이내**이며,
자차가 보관 경로에서 **2.0 m 이내**일 때만 유지. 유지 중에는 보관 시각을 갱신하지 않아
상한이 실제로 동작한다.

**효과**: 경로 급변 9회 → 1회.

### 1-6. 다차로 복귀의 granularity 통일 (`1cbe835`)

**발견**: 목표 차로 선택과 거리 회계의 단위가 어긋나 있었다.
```

회계 (calc_shift_intervals)                        : N개 구간 (오늘 업스트림으로 되돌림)
```

```

```
**기동은 9.6 m 를 한 번에 그리는데 길이 산정은 3.2 m 한 칸 기준**이었다.
이 어긋남은 오늘 `86520c7` 에서 회계만 되돌리며 만들어진 것이다.

**수정**: (i) 한 기동 쪽으로 통일 — 구간 합치기 복원.
```
lane_changing_length.min = 6.46 -> 7.65 (실제 시프트 반영)
current_dist_buffer.min  = 8.46 -> 9.65 (1회분, 단계 감소 없음)
```
**결과**: 복귀 3~4홉 → **2홉**, 누적 456/442 → **600.2 m**.
우려했던 "예약이 줄어 복귀가 늦어짐"은 안 일어났다 —
한 기동으로 처리하면 애초에 그만큼의 예약이 필요 없다.

`LC_JUDGE valid=0` 이 많은 것과의 연관도 볼 것 —

### 2-2. 궤적 무효 판정 → 비상정지

```
t=43.32  정지점 134.9 -> 71.9 m   (obstacle_stop 67.1m 등장, 막힌 차량군 인지)
t=44.4~45.1  명령 acc  -1.59 -> -2.35   (normal.min_acc -2.5 안쪽)
t=45.81  Invalid Trajectory published (deceleration is too high)
t=45.93  EMERGENCY_STOP is operated
```
주행 중 `Invalid Trajectory` 3회, `EMERGENCY_STOP` 5회.
`trajectory_checker` 의 `min_lon_accel` 임계는 **-9.8** 이라 명령 감속 -2.35 로는
설명이 안 된다. **궤적 속도 프로파일의 불연속**이 걸린 것으로 추정되나 미확인.
정지점이 한 사이클에 63 m 앞으로 튀어 들어오는 것이 발단이다.

### 2-3. 복귀 중 속도 저하 (`obstacle_slow_down`)

```
t=43.4  13.1 m/s (47 km/h)
t=48.7   7.2
t=50~52  6.4 (23 km/h 정체)
t=55.1   2.0 m/s (7 km/h)
```
`obstacle_slow_down` 이 복귀 내내 붙어 속도를 누른다. 설정:
```yaml
min_lat_margin: 0.2  ->  min_ego_velocity: 2.0
max_lat_margin: 1.0  ->  max_ego_velocity: 8.0    # 1.0m 이상 떨어져도 8 m/s 가 상한
```
측정된 6.4 m/s 를 역산하면 그때 **측방 여유 약 0.79 m**.
차로폭 3.2 m, 차폭 1.886 m 라 차로 중앙끼리면 1.3 m 인데, 복귀 중 비스듬해서 더 붙는다.

**선택지**: `max_lat_margin` 1.0 → 0.6 (감속 발동 조건을 좁힘)이 가장 근거가 명확하다.
`max_ego_velocity` 상향은 "가까이 있어도 빠르게"라 안전 논리가 약하다.

### 2-4. 기동 비결정성

`load_node` 타임아웃으로 제어 컨테이너 노드 4개
(`operation_mode_transition_manager`, `shift_decider`, `vehicle_cmd_gate`,
`trajectory_follower/controller_node_exe`)가 누락되는 일이 반복.
40초 검증이 잡아내지만 **대회 당일 시간 제약이 있으면 문제**다.
rviz 를 같이 띄우면 확률이 올라가는 것으로 보이나 표본이 적어 단정 못 함.

### 2-6. 장애물 옆 통과 감속이 3.2 m 옆 정차 차량에 안 걸린다 ★ 시나리오 1에서 발견

**기능은 원래 들어 있다.** `obstacle_slow_down`(motion_velocity_planner)이 그것이고,
보행자·차량 전부 대상(`object_type.pedestrian/car: true`)이며 통과 속도 상한을 측방 여유로 보간한다.
```
slow_down_planning.object_type_specified_params.default (좌·우 동일)
  측방 여유 0.2 m -> 2.0 m/s (정지물 4.0 m/s)
  측방 여유 1.0 m -> 8.0 m/s = 28.8 km/h   ← 사실상 "30 km/h 로 감속"이 이 값이다
```

**허점은 대상 필터의 반경이다.**
```
obstacle_filtering.max_lat_margin: 1.1   # 자차 폭 밴드에서 1.1 m 밖이면 아예 대상이 아님
```

**실측** (`test/0910_201528_sc1`, bag 에서 자차 좌표계로 재계산):

| t | 자차 속도 | 대상 | 자차 중심 기준 |
|---|---|---|---|
| 146.5 | 33.6 km/h | **정차 차량**(v=0, 4.4×1.8 m) | 종 +5.9, **횡 +3.2** |
| 147.0 | 36.6 km/h | 〃 | 종 +1.2, 횡 +3.2 |
| 147.4 | **38.0 km/h** | 〃 (바로 옆) | 종 -3.7, 횡 +3.2 |
| 148.2 | **39.9 km/h** | 〃 (지나침) | 종 -14.2, 횡 +3.2 |

횡 3.2 m → 차체 가장자리끼리 여유 = 3.2 − 0.943(자차 반폭) − 0.9(객체 반폭) ≈ **1.36 m**.
필터 임계 1.1 m 를 **0.26 m 차이로 넘겨서** 대상에서 빠졌다. 그래서 감속이 0 이고,
오히려 33.6 → 39.9 km/h 로 **가속하며** 지나갔다.

**수정 후보**: `obstacle_filtering.max_lat_margin` 1.1 → 2.5.
단 이것만 넓히면 부족하다 — 속도 보간표의 `max_lat_margin: 1.0` 도 같이 넓혀야
1.0 m 밖에서 8 m/s 상한이 그대로 이어진다(지금은 표 밖이라 제한이 안 걸린다).

**★ 2-3 과 방향이 반대다.** 2-3 은 복귀 중 과도한 감속을 풀자고 `max_lat_margin` 1.0 → 0.6
(더 좁게)을 제안했다. 두 요구가 같은 파라미터를 반대로 민다.
분리안: 옆 차로 주행 차량으로 인한 감속(2-3)은 **`moving` 쪽 파라미터**로 좁히고,
정차 차량·보행자는 **static 쪽**을 넓힌다 — 표가 `moving`/`static` 으로 이미 나뉘어 있으므로
파라미터만으로 분리 가능하다. (`static.max_lat_margin` 만 2.5, `moving` 은 0.6)

**반경은 우리 기준이다 — 규정에 해당 조항이 없다** (2026-09-10 확인).
채점표(§7C)는 **접촉했을 때만** 본다(14 도로이용자 충돌 중대 / 11 장애물 충돌 경미).
옆을 빨리 지나가는 것 자체는 감점 항목이 아니다. 그래서 이 값은 규정 준수가 아니라
**충돌 위험 대 완주 시간**의 우리 선택이다.

- 넓히면: 정차 차량·보행자 옆을 28.8 km/h 로 지난다 → 접촉 위험↓, 완주 시간↑(순위 2차 기준)
- 좁히면: 지금처럼 40 km/h 로 지난다 → 시간 유리, 횡방향 여유가 1.4 m 밖에 없는 채로 통과

**반경 산정은 30 km/h 의 제동거리에서 역산한다** (사용자 지시, 9/10).

전제 — 우리 실차 파라미터: 순항 `max_vel` 12.8 m/s(46 km/h), 감속 `normal.min_acc` **-2.5**
(9/10 실측으로 여기까지만 연 값. VTD Ioniq6 는 -2.4 근처까지만 정상 응답하고 그 밖은 과반응),
`limit.min_acc` -4.0, 지연 0.2 s 가정.

(a) **30 km/h 로 통과하려면 얼마나 앞에서 감속을 시작해야 하나** (12.8 → 8.0 m/s)

| 감속 | 감속 거리 | `time_margin_on_target_velocity` 1.5 s(=12 m) 포함 |
|---|---|---|
| **-1.0** (지금 `slow_down_min_acc`) | 49.9 m | **61.9 m** |
| -1.5 | 33.3 m | 45.3 m |
| -2.0 | 25.0 m | 37.0 m |
| -2.5 (normal 한계) | 20.0 m | 32.0 m |

(b) **그 속도에서 멈출 수 있는 거리** (보행자가 튀어나오는 경우)

| 통과 속도 | 감속 -2.5 | 감속 -4.0(limit) |
|---|---|---|
| **8.0 m/s (28.8 km/h)** | **14.4 m** | 9.6 m |
| 11.1 m/s (40 km/h, 이번 실측) | 26.8 m | 17.6 m |

**차이가 12.4 m 다.** 정차 차량 뒤에서 보행자가 나오면 확보되는 시간은
(횡 3.2 m − 자차 반폭 0.94) / 보행자 1.5 m/s ≈ **1.5 s** → 그 사이 진행거리가
30 km/h(8.0 m/s) 면 12.0 m(제동거리 14.4 m 와 비슷), 40 km/h 면 16.7 m(제동거리 26.8 m 로 **못 선다**).
**이것이 "옆에 정차물이 있으면 30 km/h" 의 근거다.**

→ **반경 결론**: 가리는 물체가 **한 차로 폭 안(횡 ~3.5 m)** 에 있으면 30 km/h.
파라미터로는 `static.max_lat_margin` **2.5 m** (차체 밴드 기준이라 중심 거리로 약 4.3 m 까지 포함).

**같이 고쳐야 할 것 — 감속률**: (a) 표에서 보듯 지금 `slow_down_min_acc: -1.0` 은
**62 m 앞에서** 감속을 시작해야 성립한다. 이번 사례의 대상 차량은 **12 m 앞에서 정지**했으므로
반경만 넓혀도 못 따라간다. `slow_down_min_acc` 를 **-2.0** 정도로(=37 m, VTD 응답 한계 -2.4 안쪽)
같이 내려야 실제로 30 km/h 가 나온다.

**적용 상태: 미적용 — 계산만 해둔 것이다** (2026-09-10, 재주행 없이 문서화만 지시).
아래 3줄이 후보이고, **실주행 검증을 안 했으므로 어디에도 반영하지 않았다.**
```yaml
# obstacle_slow_down.param.yaml
slow_down_planning.object_type_specified_params.default.{left,right}.static.max_lat_margin: 1.0 -> 2.5
obstacle_filtering.max_lat_margin:                                                          1.1 -> 2.5
slow_down_planning.slow_down_min_acc:                                                      -1.0 -> -2.0
```
검증할 때 같이 볼 것: (i) 정차물 옆 통과 속도가 8.0 m/s 이하로 눌리는가,
(ii) 완주 시간이 얼마나 늘어나는가(순위 2차 기준), (iii) 복귀 중 불필요한 감속이 늘지 않는가
(`moving` 은 그대로 두므로 2-3 과 충돌하지 않아야 한다).

**이번 사례의 성격 주의**: 그 차는 처음부터 서 있던 게 아니다.
t=143.4 에 8.5 m/s 로 달리다 오른쪽으로 빠지며 t=146.5 에 정지했다 —
**자차가 지나가기 1.5 초 전에 정차물이 된 것**이다. `moving`/`static` 판정이 늦게 뒤집히는
경우라 `successive_num_to_entry_slow_down_condition: 5`(5 사이클 연속 조건)도 같이 볼 것.

### 4-3. 주행 스크립트 중복 실행

백그라운드 ssh 로 스크립트를 실행하면 **두 개가 뜨는 일이 반복**됐다.

```bash
ssh a@... 'setsid nohup /tmp/run_xxx.sh > /tmp/run_xxx.out 2>&1 < /dev/null &'
```

`pkill -f` 는 자기 자신(ssh 원격 명령줄)을 잡을 수 있다. PID 로 죽일 것.

### 4-7. 방법론 (이번 세션에서 비싸게 배운 것)

- **넓게 켜고 볼 것.** 로거 하나만 켜두고 다른 모듈의 판단을 추측하다 시간을 버렸다.
