## 1. 지도 실측 — 이 장면의 기하 (확인)

좌우 배치(lanelet 좌/우 이웃 관계로 확인):

    왼쪽 ←                                          → 오른쪽
     P(좌회전포켓)  │  A(자차)  │  B  │  C  │  D

- 자차 차선 A 가 직진 차로 중 맨 왼쪽, 포켓 P 는 A 바로 왼쪽. **P 의 이웃은 A 뿐이다.**
- 루트 preferred: `16144 → 15719 → 15379(A) → 15194(P) → 14855(P) → 14611(P) → 18858`
  즉 A 에서 좌측 1회가 경로상 필수. `lane_change_left` 가 맞는 모듈이고 `lane_change_right` 는 정상적으로 침묵.

세그먼트 구간과 점유(A 기준 종방향, 교차로 정지선 = 0):

    　        seg2 -92.6..-60.4  seg3 -60.4..-50.3  seg4 -50.3..-17.9  seg5 -17.9..0
    P         차선 없음           빈                 빈                 빈
    A         막힘 -64.4         막힘 -57.4,-50.3    막힘 -44.1         빈
    B         빈                 막힘 -50.3         막힘 -44.1         빈
    C         빈                 빈                 빈                 빈
    D         빈                 빈                 빈                 빈

핵심 두 가지:
- **포켓 시작이 -60.4 m 인데 A 의 첫 정지차가 -64.4 m.** 포켓이 생기기 4 m 전에 막힌다.
  그 지점의 lanelet 15379 는 왼쪽 이웃이 없으므로 `lane_change_left` 가 `valid=0` 인 것은 정상이다.
- **A 가 뚫린 유일한 구간은 -44.1..-17.9 (26.2 m).** 포켓 진입은 거기서만 가능하고,
  거기까지 가려면 전 구간 비어 있는 **C** 를 거쳐야 한다(B 도 seg3·seg4 에서 막힘).
  → 필요한 기동은 A→B→C (우측 2회) + C→B→A→P (좌측 3회) = 5회.
  `lane_planner` 의 A* 가 낸 계획과 일치한다:
  `15379→15414 → 15414→15449 → 14960→14925 → 14925→14633 → 14633→14611`

상류 구간(확인):
- `16144(101.4 m) → 15719(28.1 m) → 15379(A)`, 우측 열은 `16249→15750→15414(B)`, `16354→15781→15449(C)`
- 경계 실측: `16144|16249` `16249|16354` = **dashed(변경 가능)**, `15719|15750` `15750|15781` = **solid(불가)**
- mission_planner 가 seg0·seg1 을 primitive 1개로 만든 것은 seg1 이 실선이라 맞는 판단이다.

## 2. 고친 것 (전부 실측 근거 있음)

### 2-1. `static_obstacle_avoidance` 가 차선변경을 승인 풀에서 축출하고 있었다
`scene_module_manager.param.yaml` 의 slot2 에서 avoidance 가 `lane_change_*` 보다 위이고
`enable_simultaneous_execution_as_candidate_module: false` 다. 그래서 avoidance 가 후보로 등록되는 순간
다른 모듈은 후보 자체가 될 수 없다.

실측(`appr1_0908_054138`): `lane_change_left` 가 t=20.3s 에 후보로 떴다가 **0.7초 만에** 사라지고
avoidance 만 남았다. 그리고 avoidance 는 경로를 **오른쪽으로**(횡오프셋 -2.71 m) 밀어 포켓 반대편 B 차선에서
정지시켰다. 즉 목표에서 멀어지게 만들고 있었다.

→ `default_preset.yaml` 에서 `launch_static_obstacle_avoidance: "false"`.
**원복법**: `"true"`. 그 경우 `scene_module_manager.param.yaml` 에서 avoidance 를 `lane_change_*` **아래로**
내리고 `enable_simultaneous_execution_as_candidate_module: true` 로 열어야 한다.

### 2-2. `lane_planner` 의 RTC 승인이 세션 내내 한 번도 전송되지 않았다
RTC 승인 서비스는 모듈마다 따로 만들어진다:

    rtc_interface.cpp:142   cooperate_commands_namespace_ + "/" + name
    → /planning/cooperate_commands/external_request_lane_change_right

`lane_planner.py` 는 접미사 없는 `/planning/cooperate_commands` 로 클라이언트를 만들고 있었다.
`service_is_ready()` 가 항상 false 이고 `send_rtc()` 는 **조용히 반환**하도록 돼 있어 로그도 남지 않았다.

→ 방향별 클라이언트로 수정 + 못 보낸 이유를 경고로 남기도록 수정(`lane_planner.py`).
수정 후 `RTC 승인 전송: right 1건` 이 실제로 나갔고, **오늘 처음으로 차선변경 모듈이 RUNNING 에 들어갔다.**

### 2-3. 깜빡이 타이머가 죽어 있어 준비시간이 4.0 s 에 고정돼 있었다 (가장 큰 건)

    prepare = max(max_prepare_duration - active_signal_duration, min_prepare)

`active_signal_duration` 이 항상 0 이었다. 원인은 두 곳:
- `scene.cpp get_current_turn_signal_info()` 가 `status_.is_valid_path` 가 참일 때만 타이머를 시작했다.
  그런데 유효 경로가 없어도 그 분기는 **깜빡이를 실제로 켠다**(`get_turn_signal` 반환. 실측: `turn=2` 가 100초 이상 지속).
  즉 깜빡이는 켜져 있는데 그 시간을 세지 않고 있었다.
- `interface.cpp` 의 `!isValidPath()` 분기가 매 주기 `resetParameters()` 를 불러 타이머를 지웠다(한 판에 3800회).

→ 타이머 시작을 `is_valid_path` 검사 **앞으로** 옮기고, `resetParameters(bool keep_signal_timer)` 를 도입해
`invalidPath` 리셋에서는 타이머를 보존한다(모듈 종료·변경 완료에서만 지운다).
`base_class.hpp`/`scene.hpp` 선언, `scene.cpp`/`interface.cpp` 구현 수정.

**효과(같은 속도에서 실측)**:

    v=13.90  준비=3.81s(52.9m)  필요=60.5m  valid=0
    v=13.88  준비=3.31s(45.9m)  필요=53.5m  valid=1
    v=13.75  준비=2.21s(30.4m)  필요=38.0m  valid=1
    v= 8.87  준비=0.50s( 4.4m)  필요=12.0m  valid=1     ← 60.5 m → 12.0 m

주의(확인): 저속에서는 효과가 없다. `min_prepare` 가 `(2.78 - v)/max_acc` 라 v=0 이면 5.56 s 로,
`max(4.0 - t, 5.56) = 5.56` 이 되어 타이머가 무의미하다. 이 수정은 **정상 속도 구간용**이다.

## 3. 폐기한 접근 (근거 있음 — 다시 시도하지 말 것)

### 3-1. 웨이포인트로 우회를 표현하는 것 — 원리적으로 무효
`set_route_points` 는 이웃 차선들을 **한 세그먼트로 묶고**, 그 안에서 어느 차선을 탈지는 mission_planner 가
`preferred_primitive` 로 혼자 정한다. behavior_path 는 preferred 를 따라간다.
실측: C 차선에 웨이포인트를 찍었더니 세그먼트 2 의 4개 primitive 안에 이미 포함돼 있어
**루트가 한 글자도 바뀌지 않았다**(preferred 열이 원래와 완전히 동일).

### 3-2. `external_request_lane_change_*` — 껐다
루트와 무관하게 항상 "변경이 필요하다"고 주장하므로 반대 방향 후보를 계속 낸다.
승인된 모듈들이 **각자 정지점을 꽂아** 교착된다.
실측(`h4_pocket_ext2_0908`): `lane_change_right` 15.7 m 와 `external_..._left` 1.6 m 가 동시에 정지를 넣고
이어서 `obstacle_stop` 1.75 m 로 고착.
→ `default_preset.yaml` 에서 좌·우 모두 `"false"`. **원복법**: `"true"`.

### 3-3. 저속 주행으로 성립시키기 — 해결이 아님
3.2 m/s 로 낮추면 첫 변경 A→B 는 성공하지만 연속된 두 번째 B→C 는 여전히 실패한다.
그리고 채점의 시간 항목을 깎고 일반 상황에 이식되지 않는다. 진단용으로만 쓸 것.

## 4. 유효하지만 제약이 있는 수단 — `change_route` 로 preferred 교체 (확인)

`/api/routing/change_route` (타입 `SetRoute`, 세그먼트마다 `preferred` + `alternatives`)로
주행 중 preferred 를 바꿀 수 있다. `success=True` 확인.
`route_handler.cpp:558-570` 은 메시지에 든 primitive 를 그대로 쓰므로,
**이웃 묶음은 그대로 두고 preferred 만 바꾸면** 차선변경 가능성을 유지한 채 경로를 조향할 수 있다.
(route_node 의 "명시 세그먼트는 차선변경 불가" 기록은 primitive 1개짜리로 만들었을 때만 맞다.)

제약(확인): `calc_shift_intervals`(calculation.cpp:288)는 **`current_lanes.back()`** 에서
preferred 까지의 횡간격을 구한다. 못 찾으면 빈 벡터 → 필요 길이 `DBL_MAX` → 후보 전멸.
- 차선열 끝이 `14633(A)`, 그 preferred 가 `14611(P)`(왼쪽)이면 → **우측은 항상 무한대**.
- preferred 를 **전 구간 C** 로 바꾸면 `lane_change_right` 가 `valid=1` 로 살아난다(실측 확인).
→ 즉 우회는 "하류 끝단까지 일관되게 C" 로 두어야 표현된다. 단계 전환(C → P)은 별도 `change_route` 로.

`is_reroute_available` (behavior_path_planner_node.cpp:556)은 lane_following 외 모듈이 승인·실행 중이면
false 다. 재라우팅은 그때를 피해서 넣어야 한다. SET 상태에서는 `set_route_points` 가 거부되므로
`change_route`/`change_route_points` 를 쓴다.

## 5. 남은 벽 (다음 세션의 출발점)

### 5-1. RSS 가 "앞차" 때문에 unsafe 를 낸다 — 우리는 그 앞차를 피하려는 것인데
계측(`[HLFMA-S]`): `normal RSS unsafe: ego_stuck=0 막는객체_후행=0 v_prepare=13.60`
- `막는객체_후행=0` → 막는 것은 앞차(뒤차 아님)
- `ego_stuck=0` → 갇힘 전용 완화 RSS(`rss_params_for_stuck`)가 **한 번도 적용되지 않는다**

`is_ego_stuck()`(scene.cpp:2001)은 ① 속도 < `th_stop_velocity` ② 정지 유지 ≥ `th_stop_time`
③ 전방에 정지 객체 — 세 조건이라 **자차가 실제로 멈춘 뒤에만** 참이 된다. 언제나 사후적이다.
그래서 유효 경로는 v=13.9 부터 있는데 승인은 v≈4.3 까지 감속한 뒤에야 나고, 그때는 이미
정지차 코앞이라 두 번째 변경이 들어갈 자리가 없다(후보 t=24.8s → 승인 t=31.0s, 그 사이 55 m 소진).

### 5-2. 변경 도중 정지하면 모듈이 `RUNNING` 에 영구 고착한다
실측: `lane_change_right(RUNNING)` 이 t=32.9s 부터 주행 끝(125초)까지 유지.
`hasFinishedLaneChange()` 는 변경 경로 끝에 도달해야 참인데 자차가 중간에 멈추면 영원히 거짓이다.
승인 슬롯을 물고 있어 두 번째 변경은 검토조차 되지 않고 재계획도 없다.
그 정지를 넣은 것은 모듈 자신이다 — `"next lc terminal"`(다음 변경이 48 m 앞 종점까지 못 들어감).

**지금 이 교착을 풀 수단이 없다.** `lane_change_left/right` 는 `enable_rtc: false` 라 외부에서
취소(DEACTIVATE)할 수 없다. 상위 노드가 "실패했으니 물러나고 다시 계획하라"고 말할 창구가 없다.

### 5-3. 상위 중재의 실제 손잡이 (조사 결과)
4개 인스턴스(NORMAL/EXTERNAL × 좌/우)는 preset 으로 기동 시 생성되어 런타임에 생성·소멸할 수 없다.
상위 노드가 쥘 수 있는 것은 셋뿐이다:

| 손잡이 | 수단 | 정하는 것 |
|---|---|---|
| 방향·필요성 | `change_route` (preferred 교체) | NORMAL 이 어느 방향을 필수로 볼지 |
| 실행 허가·인터럽트 | `/planning/cooperate_commands/<모듈명>` ACTIVATE/DEACTIVATE | `enable_rtc: true` 인 모듈만 |
| 성립 가능성 | 속도 상한 | 준비거리 = v × prepare |

"지금 실행하라"는 API 는 없다. 보장은 상위 노드가 결과를 관측하고 재계획하는 것으로만 만들 수 있다.

### 5-4. 프레넷은 종점 근처에서만 쓰인다
`scene.cpp:1199`: `if (frenet.enable && is_ego_near_current_terminal_start) → get_path_using_frenet(...)`
평상시에는 `path_shifter`(준비구간 + 고정 시프트)로 간다. 빠듯한 구간에 약하다.
미검토 대안: 고전 샘플러가 후보 0개일 때 프레넷으로 폴백하도록 조건 확장(업스트림 동작 변경, 하류 재검증 필요).

## 6. 기술부채 (원복법 포함)

1. **임시 계측 로그** — 진단 끝나면 제거할 것
   - `scene.cpp`: `[HLFMA-A]`(유효성·길이), `[HLFMA-B]`(후보 accept/reject), `[HLFMA-PREP]`(준비시간·깜빡이),
     `[HLFMA-S]`(RSS 안전 판정)
   - `interface.cpp`: `[HLFMA-R]`(리셋 지점), `[HLFMA]`(not required 사유)
2. **`static_obstacle_avoidance` off** — §2-1 원복법 참조. 이 지도에 `road_shoulder` 가 없어 차선 내 회피는
   어차피 불가하지만, 인접 차선을 쓰는 시프트는 되므로 다른 장면에서는 쓸모가 있을 수 있다.
3. **`external_request_lane_change_*` off** — §3-2 원복법 참조. 켜려면 동시 실행 중재를 먼저 넣어야 한다.
4. **깜빡이 타이머 수정은 업스트림 동작 변경** — 되돌리려면 `scene.cpp` 의 `set_signal_activation_time()` 을
   `!is_valid_path` 분기 **뒤로** 되돌리고 `interface.cpp` 의 `resetParameters(true)` 를 `resetParameters()` 로.
   다른 시나리오(정상 차선변경)에서의 부작용은 아직 확인하지 않았다.
5. **속도 상한 실험값** — `h4_pocket_slow.conf` 의 `VEL_LIMIT=3.2` 는 진단용이다. 처방 아님.
6. **미해결(이월)**: 자차 속도 50 km/h 초과(실측 55~60 km/h, 1.3~2.0 s) — 채점 1번 항목 위험.
   MRM/STALE 간헐 발생. 둘 다 이번 세션에서 손대지 않았다.

## 7. 다음 세션에서 할 것 (우선순위)

1. **교착 해소 수단 확보** — `lane_change_left/right` 에 `enable_rtc: true` 를 켜고,
   상위 노드가 정체(변경 RUNNING 인데 자차 정지가 N 초 지속)를 감지해 DEACTIVATE → 재계획.
   부작용: RTC 를 켜면 승인자가 없을 때 아예 실행이 안 되므로 승인 로직이 반드시 함께 있어야 한다.
2. **`is_ego_stuck` 을 선행적으로 만들지 검토** — "전방 정지 객체가 제동거리 안에 있고 통과 불가"를
   정지 전에 판정. 업스트림 변경이므로 영향 범위를 먼저 정리할 것.
3. **`lane_planner` 를 단계 전환기로 개편** — 출력이 외부 RTC 요청이 아니라 `change_route`(preferred 교체)가
   되도록. 1단계 전 구간 C → 정지차 통과 확인 → 2단계 preferred 를 P 로 되돌려 복귀.
   `is_reroute_available` 을 보고 넣을 것.
4. 위 셋이 붙으면 `h4_pocket` 케이스로 완주 검증 → 그 다음에 VTD 실주행 1회로 대조.
5. 이월 과제(속도 초과, MRM/STALE).
