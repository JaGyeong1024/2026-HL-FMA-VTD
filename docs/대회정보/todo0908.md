### 포켓 진입 — 마지막 한 칸이 남은 지점 (다음 사람이 여기서 이어가면 된다)

현재 동작 (`LANE_PLAN=true bash tools/harness/h4_pocket.sh h4_auto`, 수동 주입 없음):

    16144 → 15719 → 15379(A) → 15414(B) → 15220(B) → 14925(B) → 14655(B) → 14633(A)
    [44.0s] A→B 우회   [57.5s] B→A 복귀   최고속 50.3 km/h
    정지차 4대 통과, 어떤 모듈도 정지를 넣지 않음. 자차는 정지선까지 도달.

**남은 것은 A→포켓 한 칸이다. 원인은 거리 부족이 아니라 모듈의 실행 지연이다.**

실측 (정지선까지 남은 거리 기준):

    t=44.0s   72.0 m   A→B 우회
    t=49.5s  ~44   m   마지막 정지차(obj14, s=-44.1) 통과 — 여기서부터 A 가 비어 있다
    t=50.0s   41.6 m   v=28.1 km/h   ← B→A 를 시작했어야 할 지점
    t=55.0s   16.9 m   v=13.9 km/h
    t=57.5s    8.5 m   B→A 복귀      ← 33 m 를 흘려보낸 뒤에야 시작
    t=63.0s    5.4 m   정지

마지막 정지차를 지난 시점에 **44 m** 가 남아 있었고 필요한 것은 2회 × 9~11 m = **약 22 m** 였다.
두 배 여유가 있었는데 모듈이 **33 m 동안 아무것도 하지 않았다.**
(앞서 "seg5 가 17.9 m 뿐이라 자리가 없다"고 적었던 것은 결과를 원인으로 착각한 설명이다. 정정한다.)

역할 구분을 분명히 해 둘 것:

| | 하는 일 |
|---|---|
| A* (`lane_planner`) | 어느 차선을 거쳐 갈지만 정한다. 점유 lanelet 을 피한 시퀀스를 낸다 |
| 경로 표현 | 그 시퀀스를 `set_preferred_primitive` 로 루트 preferred 에 쓴다 |
| `lane_change_left/right` | **실제 기동.** 준비 구간·횡 시프트·안전 판정·실행 시점은 전부 이쪽이 정한다 |

A* 는 "B 로 갔다가 A 로 돌아와 포켓"이라고 **말할** 뿐이고, 언제 핸들을 꺾을지는 모듈이 정한다.
이번 33 m 지연은 정확히 그 경계에서 생겼다. 따라서 A* 를 더 손봐도 해결되지 않는다.

**33 m 정체의 실제 사슬 (계측 확정)**

    bag 18.8s  lane_change_right RUNNING 시작 (v=13.9)   ← 첫 정지차 코앞에서야 시작
    bag 17.7s  "maintain distance to front object" → 정지점 삽입 (거리 0.05 m)
    bag 21.1s  lane_change_left 가 후보로 뜸 (WAITING_APPROVAL)
    bag 30.0s  v=2.92 — 감속
    bag 34.4s  lane_change_right 완료. 15.6초 붙들었다
    bag 34.5s  lane_change_left RUNNING — 그제서야 복귀 시작

A→B 기동을 **첫 정지차 코앞에서 시작**한다. 준비 구간 동안 자차는 아직 A 차선이고 그 앞에
정지차가 있으니, 모듈이 거리 유지를 위해 정지점을 넣는다(**정상 동작이다. 건드리지 말 것**).
그러면 감속 → 기동이 안 끝남 → `RUNNING` 유지 → 복귀는 후보로만 대기.
§5-2 의 "변경 도중 정지 → RUNNING 고착" 패턴 그대로다.

**따라서 진짜 질문은 "왜 우회를 늦게 시작하나"이다.** 요구(반영 1)는 출발 전 t=0 에 이미
나갔는데 모듈은 mock t≈44 까지 기다렸다.

기각된 가설 두 개 (다시 시도하지 말 것):
- ~~RSS 가 복귀를 거부한다~~ — 후보는 정상적으로 떴다. 승인 슬롯 점유가 막은 것이다.
- ~~실행 중 재라우팅이 모듈을 꼬았다~~ — 재라우팅 금지 게이트를 넣어도 15.6초 붙드는 것은 동일했다.
  (게이트 자체는 실제 위험을 막으므로 남겨 뒀다.)

**기각된 방향: 정체된 기동을 중단시키기**

RUNNING 을 밖에서 끊는 것은 위험하다(두 차선에 걸친 상태에서 경로가 튕겨 돌아가 횡저크 →
항목 3·4). Autoware 는 `isAbortState()`/`abort_path_`/`cancel` RSS 로 **스스로** 포기하는
장치를 갖고 있고, 그게 올바른 방식이다.

그리고 **우리 경우엔 중단 방향 자체가 이득이 없다.** A→B 기동은 결국 완료됐다. 실패가 아니라
오래 걸린 것뿐이고, 여기서 중단시키면 자차는 A 차선 = 정지차 4대 뒤에 그대로 남는다.
지금보다 나쁘다.

(시간 기반 타임아웃은 특히 근거가 없다 — 기동 시간은 속도·거리·주변 차량에 따라 다르다.
굳이 판정하려면 기하 기준, 즉 "남은 거리 < 남은 기동에 아직 필요한 거리"여야 하고
그 값은 `calc_lc_length_and_dist_buffer` 가 이미 계산한다.)

**남은 지렛대는 하나다 — 우회를 더 일찍 시작하기.**

요구(반영 1)는 출발 전 t=0 에 나갔는데 모듈은 mock t≈44, 첫 정지차 코앞에서야 시작했다.
30 m 만 일찍 시작하면 준비 구간에 앞차가 없어 기동이 빨리 끝나고, 복귀·포켓 진입에
44 m 가 온전히 남는다. 원인과 해결이 한 줄로 이어진다.

1. **왜 늦게 시작하는지 계측.** 유력한 것은 `isLaneChangeRequired` 의
   `ego_dist_to_target_start > max_prepare_length` (= `max_prepare_duration 4.0 × max_vel 13.6`
   = 54.4 m). 목표 차선 시작에서 54.4 m 안에 들어와야 검토를 시작한다.
   `[HLFMA-A]`·`[HLFMA-B]` 를 우회 시작 전 구간에만 되살려 확인할 것. 커밋 `5dcdb4b` 의 역패치.
   **주의**: `max_prepare_duration` 을 키우면 규제요소 근접 판정이 반대로 빡빡해져 차선변경이
   막힌다. 9/7 과 9/8 오전에 각각 한 번씩 이 함정에 빠졌다(부록 B-2). 계측 먼저.
2. **회피 직후 구간 속도 하향.** 늦게 시작해도 1회 길이가 줄어 들어간다. `speed_candidates`
   가 이미 있다. 근본 해결은 아니지만 대회까지 시간이 없으면 이쪽이 확실하다.
3. `restore_route()` 를 "원경로 전방이 비면 즉시"로 앞당기기 (보조).

## 1. 지도 실측 — 이 장면의 기하 (확인)

좌우 배치(lanelet 좌/우 이웃 관계로 확인):

    왼쪽 ←                                          → 오른쪽
     P(좌회전포켓)  │  A(자차)  │  B  │  C  │  D

- 자차 차선 A 가 직진 차로 중 맨 왼쪽, 포켓 P 는 A 바로 왼쪽. **P 의 이웃은 A 뿐이다.**
- 루트 preferred: `16144 → 15719 → 15379(A) → 15194(P) → 14855(P) → 14611(P) → 18858`
  즉 A 에서 좌측 1회가 경로상 필수. `lane_change_left` 가 맞는 모듈이고 `lane_change_right` 는 정상적으로 침묵.

세그먼트 구간과 점유(A 기준 종방향, 교차로 정지선 = 0):

    　        seg2 -92.6..-60.4  seg3 -60.4..-50.3  seg4 -50.3..-17.9  seg5 -17.9..0
    P         차선 없음           빈                 빈                 빈
    A         막힘 -64.4         막힘 -57.4,-50.3    막힘 -44.1         빈
    B         빈                 막힘 -50.3         막힘 -44.1         빈
    C         빈                 빈                 빈                 빈
    D         빈                 빈                 빈                 빈

핵심 두 가지:
- **포켓 시작이 -60.4 m 인데 A 의 첫 정지차가 -64.4 m.** 포켓이 생기기 4 m 전에 막힌다.
  그 지점의 lanelet 15379 는 왼쪽 이웃이 없으므로 `lane_change_left` 가 `valid=0` 인 것은 정상이다.
- **A 가 뚫린 유일한 구간은 -44.1..-17.9 (26.2 m).** 포켓 진입은 거기서만 가능하고,
  거기까지 가려면 전 구간 비어 있는 **C** 를 거쳐야 한다(B 도 seg3·seg4 에서 막힘).
  → 필요한 기동은 A→B→C (우측 2회) + C→B→A→P (좌측 3회) = 5회.
  `lane_planner` 의 A* 가 낸 계획과 일치한다:
  `15379→15414 → 15414→15449 → 14960→14925 → 14925→14633 → 14633→14611`

상류 구간(확인):
- `16144(101.4 m) → 15719(28.1 m) → 15379(A)`, 우측 열은 `16249→15750→15414(B)`, `16354→15781→15449(C)`
- 경계 실측: `16144|16249` `16249|16354` = **dashed(변경 가능)**, `15719|15750` `15750|15781` = **solid(불가)**
- mission_planner 가 seg0·seg1 을 primitive 1개로 만든 것은 seg1 이 실선이라 맞는 판단이다.

`scene_module_manager.param.yaml` 의 slot2 에서 avoidance 가 `lane_change_*` 보다 위이고
`enable_simultaneous_execution_as_candidate_module: false` 다. 그래서 avoidance 가 후보로 등록되는 순간
다른 모듈은 후보 자체가 될 수 없다.

실측(`appr1_0908_054138`): `lane_change_left` 가 t=20.3s 에 후보로 떴다가 **0.7초 만에** 사라지고
avoidance 만 남았다. 그리고 avoidance 는 경로를 **오른쪽으로**(횡오프셋 -2.71 m) 밀어 포켓 반대편 B 차선에서
정지시켰다. 즉 목표에서 멀어지게 만들고 있었다.

→ `default_preset.yaml` 에서 `launch_static_obstacle_avoidance: "false"`.
**원복법**: `"true"`. 그 경우 `scene_module_manager.param.yaml` 에서 avoidance 를 `lane_change_*` **아래로**
내리고 `enable_simultaneous_execution_as_candidate_module: true` 로 열어야 한다.

### 2-2. `lane_planner` 의 RTC 승인이 세션 내내 한 번도 전송되지 않았다
RTC 승인 서비스는 모듈마다 따로 만들어진다:

    rtc_interface.cpp:142   cooperate_commands_namespace_ + "/" + name
    → /planning/cooperate_commands/external_request_lane_change_right

`lane_planner.py` 는 접미사 없는 `/planning/cooperate_commands` 로 클라이언트를 만들고 있었다.
`service_is_ready()` 가 항상 false 이고 `send_rtc()` 는 **조용히 반환**하도록 돼 있어 로그도 남지 않았다.

→ 방향별 클라이언트로 수정 + 못 보낸 이유를 경고로 남기도록 수정(`lane_planner.py`).
수정 후 `RTC 승인 전송: right 1건` 이 실제로 나갔고, **오늘 처음으로 차선변경 모듈이 RUNNING 에 들어갔다.**

### 2-3. 깜빡이 타이머가 죽어 있어 준비시간이 4.0 s 에 고정돼 있었다 (가장 큰 건)

    prepare = max(max_prepare_duration - active_signal_duration, min_prepare)

`active_signal_duration` 이 항상 0 이었다. 원인은 두 곳:
- `scene.cpp get_current_turn_signal_info()` 가 `status_.is_valid_path` 가 참일 때만 타이머를 시작했다.
  그런데 유효 경로가 없어도 그 분기는 **깜빡이를 실제로 켠다**(`get_turn_signal` 반환. 실측: `turn=2` 가 100초 이상 지속).
  즉 깜빡이는 켜져 있는데 그 시간을 세지 않고 있었다.
- `interface.cpp` 의 `!isValidPath()` 분기가 매 주기 `resetParameters()` 를 불러 타이머를 지웠다(한 판에 3800회).

→ 타이머 시작을 `is_valid_path` 검사 **앞으로** 옮기고, `resetParameters(bool keep_signal_timer)` 를 도입해
`invalidPath` 리셋에서는 타이머를 보존한다(모듈 종료·변경 완료에서만 지운다).
`base_class.hpp`/`scene.hpp` 선언, `scene.cpp`/`interface.cpp` 구현 수정.

**효과(같은 속도에서 실측)**:

    v=13.90  준비=3.81s(52.9m)  필요=60.5m  valid=0
    v=13.88  준비=3.31s(45.9m)  필요=53.5m  valid=1
    v=13.75  준비=2.21s(30.4m)  필요=38.0m  valid=1
    v= 8.87  준비=0.50s( 4.4m)  필요=12.0m  valid=1     ← 60.5 m → 12.0 m

주의(확인): 저속에서는 효과가 없다. `min_prepare` 가 `(2.78 - v)/max_acc` 라 v=0 이면 5.56 s 로,
`max(4.0 - t, 5.56) = 5.56` 이 되어 타이머가 무의미하다. 이 수정은 **정상 속도 구간용**이다.

## 3. 폐기한 접근 (근거 있음 — 다시 시도하지 말 것)

### 3-1. 웨이포인트로 우회를 표현하는 것 — 원리적으로 무효
`set_route_points` 는 이웃 차선들을 **한 세그먼트로 묶고**, 그 안에서 어느 차선을 탈지는 mission_planner 가
`preferred_primitive` 로 혼자 정한다. behavior_path 는 preferred 를 따라간다.
실측: C 차선에 웨이포인트를 찍었더니 세그먼트 2 의 4개 primitive 안에 이미 포함돼 있어
**루트가 한 글자도 바뀌지 않았다**(preferred 열이 원래와 완전히 동일).

### 3-2. `external_request_lane_change_*` — 껐다
루트와 무관하게 항상 "변경이 필요하다"고 주장하므로 반대 방향 후보를 계속 낸다.
승인된 모듈들이 **각자 정지점을 꽂아** 교착된다.
실측(`h4_pocket_ext2_0908`): `lane_change_right` 15.7 m 와 `external_..._left` 1.6 m 가 동시에 정지를 넣고
이어서 `obstacle_stop` 1.75 m 로 고착.
→ `default_preset.yaml` 에서 좌·우 모두 `"false"`. **원복법**: `"true"`.

### 3-3. 저속 주행으로 성립시키기 — 해결이 아님
3.2 m/s 로 낮추면 첫 변경 A→B 는 성공하지만 연속된 두 번째 B→C 는 여전히 실패한다.
그리고 채점의 시간 항목을 깎고 일반 상황에 이식되지 않는다. 진단용으로만 쓸 것.

## 4. 유효하지만 제약이 있는 수단 — `change_route` 로 preferred 교체 (확인)

`/api/routing/change_route` (타입 `SetRoute`, 세그먼트마다 `preferred` + `alternatives`)로
주행 중 preferred 를 바꿀 수 있다. `success=True` 확인.
`route_handler.cpp:558-570` 은 메시지에 든 primitive 를 그대로 쓰므로,
**이웃 묶음은 그대로 두고 preferred 만 바꾸면** 차선변경 가능성을 유지한 채 경로를 조향할 수 있다.
(route_node 의 "명시 세그먼트는 차선변경 불가" 기록은 primitive 1개짜리로 만들었을 때만 맞다.)

제약(확인): `calc_shift_intervals`(calculation.cpp:288)는 **`current_lanes.back()`** 에서
preferred 까지의 횡간격을 구한다. 못 찾으면 빈 벡터 → 필요 길이 `DBL_MAX` → 후보 전멸.
- 차선열 끝이 `14633(A)`, 그 preferred 가 `14611(P)`(왼쪽)이면 → **우측은 항상 무한대**.
- preferred 를 **전 구간 C** 로 바꾸면 `lane_change_right` 가 `valid=1` 로 살아난다(실측 확인).
→ 즉 우회는 "하류 끝단까지 일관되게 C" 로 두어야 표현된다. 단계 전환(C → P)은 별도 `change_route` 로.

`is_reroute_available` (behavior_path_planner_node.cpp:556)은 lane_following 외 모듈이 승인·실행 중이면
false 다. 재라우팅은 그때를 피해서 넣어야 한다. SET 상태에서는 `set_route_points` 가 거부되므로
`change_route`/`change_route_points` 를 쓴다.

## 5. 남은 벽 (다음 세션의 출발점)

### 5-1. RSS 가 "앞차" 때문에 unsafe 를 낸다 — 우리는 그 앞차를 피하려는 것인데
계측(`[HLFMA-S]`): `normal RSS unsafe: ego_stuck=0 막는객체_후행=0 v_prepare=13.60`
- `막는객체_후행=0` → 막는 것은 앞차(뒤차 아님)
- `ego_stuck=0` → 갇힘 전용 완화 RSS(`rss_params_for_stuck`)가 **한 번도 적용되지 않는다**

`is_ego_stuck()`(scene.cpp:2001)은 ① 속도 < `th_stop_velocity` ② 정지 유지 ≥ `th_stop_time`
③ 전방에 정지 객체 — 세 조건이라 **자차가 실제로 멈춘 뒤에만** 참이 된다. 언제나 사후적이다.
그래서 유효 경로는 v=13.9 부터 있는데 승인은 v≈4.3 까지 감속한 뒤에야 나고, 그때는 이미
정지차 코앞이라 두 번째 변경이 들어갈 자리가 없다(후보 t=24.8s → 승인 t=31.0s, 그 사이 55 m 소진).

### 5-2. 변경 도중 정지하면 모듈이 `RUNNING` 에 영구 고착한다
실측: `lane_change_right(RUNNING)` 이 t=32.9s 부터 주행 끝(125초)까지 유지.
`hasFinishedLaneChange()` 는 변경 경로 끝에 도달해야 참인데 자차가 중간에 멈추면 영원히 거짓이다.
승인 슬롯을 물고 있어 두 번째 변경은 검토조차 되지 않고 재계획도 없다.
그 정지를 넣은 것은 모듈 자신이다 — `"next lc terminal"`(다음 변경이 48 m 앞 종점까지 못 들어감).

**지금 이 교착을 풀 수단이 없다.** `lane_change_left/right` 는 `enable_rtc: false` 라 외부에서
취소(DEACTIVATE)할 수 없다. 상위 노드가 "실패했으니 물러나고 다시 계획하라"고 말할 창구가 없다.

### 5-3. 상위 중재의 실제 손잡이 (조사 결과)
4개 인스턴스(NORMAL/EXTERNAL × 좌/우)는 preset 으로 기동 시 생성되어 런타임에 생성·소멸할 수 없다.
상위 노드가 쥘 수 있는 것은 셋뿐이다:

| 손잡이 | 수단 | 정하는 것 |
|---|---|---|
| 방향·필요성 | `change_route` (preferred 교체) | NORMAL 이 어느 방향을 필수로 볼지 |
| 실행 허가·인터럽트 | `/planning/cooperate_commands/<모듈명>` ACTIVATE/DEACTIVATE | `enable_rtc: true` 인 모듈만 |
| 성립 가능성 | 속도 상한 | 준비거리 = v × prepare |

"지금 실행하라"는 API 는 없다. 보장은 상위 노드가 결과를 관측하고 재계획하는 것으로만 만들 수 있다.

### 5-4. 프레넷은 종점 근처에서만 쓰인다
`scene.cpp:1199`: `if (frenet.enable && is_ego_near_current_terminal_start) → get_path_using_frenet(...)`
평상시에는 `path_shifter`(준비구간 + 고정 시프트)로 간다. 빠듯한 구간에 약하다.
미검토 대안: 고전 샘플러가 후보 0개일 때 프레넷으로 폴백하도록 조건 확장(업스트림 동작 변경, 하류 재검증 필요).

# 추가 (9/8 오후) — 회피 완주 성공. 성립 조건과 남은 경우

앞의 §5 "남은 벽"은 **자차 차선과 인접 차선이 동시에 막힌 경우**에만 해당한다.
인접 차선이 비어 있는 정상적인 경우는 아래 구성으로 **완주한다**.

## 성공 케이스: 자차 차선 정지차 4대, 인접 차선 비어 있음 (`h4_pocket_aonly`)

    lanelet 열: 16144 → 15719 → 15750 → 15414(B) → 15220(B) → 14925(B)
                → 14890(A) → 14633(A) → 14611(포켓) → 18858(좌회전) → … → 18337(종점)
    차선전환:   [37.5s] A→B (상류)   [49.5s] B→A (정지차 통과 후)   [55.5s] A→포켓
    최고속 49.2 km/h,  종료 route=3(ARRIVED)

정지차를 옆 차선으로 비켜 지나가고, 복귀한 뒤, 좌회전 포켓에 진입해 좌회전을 마치고 경로 끝까지 갔다.
저속 크롤링 없이 정상 속도다. 역할 분담이 의도대로 동작한다 —
**avoidance = 정지차 비켜가기, lane_change_left = 포켓 진입.**

## 성립에 필요했던 것 (전부 실측 근거)

1. **`static_obstacle_avoidance` 를 slot2 에서 `lane_change_*` 아래로 + candidate 동시실행 열기**
   (`scene_module_manager.param.yaml`). 위에 있으면 avoidance 가 후보로 뜨는 순간 lane_change 가
   후보에서 축출된다(실측 0.7초). 포켓 진입은 lane_change_left 만 할 수 있으므로 그쪽이 우선이어야 한다.
   avoidance 자체는 preset 에서 다시 **켰다** — 정지차를 실제로 비켜간 유일한 모듈이다.
2. **`external_request_lane_change_*` 끄기.** 루트와 무관하게 반대 방향 후보를 계속 내
   승인된 모듈들이 각자 정지점을 꽂아 교착시킨다.
3. **깜빡이 타이머 복구**(업스트림). 차선변경 필요 길이 60.5 m → 12.0 m.

## B-4. 자차 속도 추정 — 이전 기록 정정

"실측 55~60 km/h"는 **차량의 실제 속도가 아니라 우리 추정기의 잡음**이다.

- VTD 패킷(1109 B)에 **자차 속도가 없다**(`<6f>` = x,y,z,heading,pitch,roll). NPC 객체만 speed 를 준다.
  자차는 객체 목록에도 없다(600 프레임 확인, 0건). 위치 차분 추정이 유일한 방법이다.
- pose 샘플이 **약 4개마다 하나씩 규칙적으로 누락**되고 그때 위치 변화가 2배가 된다. 패킷 도착이 몰리면
  dt 가 짧게 측정돼 과대 속도가 나온다(9/8 오전에 고친 194 m/s 스파이크와 같은 원인의 약한 버전.
  클램프가 30 m/s = 108 km/h 라 60 km/h 대는 통과한다).
- 실측: 지속 **50.4 km/h**, 그 위는 **0.2~0.6초 스파이크**. 채점은 VTD 자체 속도 기준이라 점수에는 안 들어간다.
- 다만 **제어기가 이 잡음을 본다.** dt 가 공칭 0.04 s 에서 벗어난 샘플 배제 등 강건화가 남은 과제.

# 부록 C — 회피 실패의 원인 사슬과 해법 (9/8)

## 증상

자차 차선에 정지차가 서 있으면 그 뒤에 멈춰 못 지나간다. 좌회전 포켓에도 들어가지 못한다.
차선변경 모듈은 **후보는 만드는데 한 번도 승인되지 않았다.**

## 원인 사슬 — 다섯 겹이었다

벽이 하나가 아니라 다섯이었고, 앞의 것을 뚫어야 뒤의 것이 보였다. 그래서 하루가 걸렸다.

### 1겹. 후보 자격을 뺏기고 있었다
`static_obstacle_avoidance` 가 slot2 에서 `lane_change_*` 보다 **위**이고
`enable_simultaneous_execution_as_candidate_module: false` 다. avoidance 가 후보로 등록되는 순간
다른 모듈은 후보가 될 수 없다. 실측: `lane_change_left` 가 후보로 뜬 지 **0.7초 만에** 사라졌다.
게다가 avoidance 는 경로를 **오른쪽으로**(횡 −2.71 m) 밀어 좌회전 포켓 반대편에 세웠다.

### 2겹. 우회를 원리적으로 표현할 수 없었다
`calc_shift_intervals` 는 `current_lanes.back()` — 차선열 **맨 끝** — 에서 preferred 까지의 횡간격을 구한다.
우리 차선열 끝은 `14633(A)` 이고 그 preferred 는 `14611(P)`, 즉 **왼쪽**이다. 그래서

    dir=좌 : 왼쪽으로 걸어 14611 발견 → 간격 [3.2] → 길이 7.6 m   (유한)
    dir=우 : 오른쪽으로 B,C,D 를 다 걸어도 preferred 없음 → 빈 벡터 → DBL_MAX

**목표 차선에서 잠시 멀어지는 기동은 어떤 지도에서도 만들 수 없다.** preferred 를 B 로도 C 로도
바꿔봤으나 끝단이 포켓인 한 동일했다. 이것이 "우회"가 구조적으로 불가능했던 진짜 이유다.

### 3겹. 기동 길이가 너무 길었다
`prepare = max(max_prepare_duration − active_signal_duration, min_prepare)` 인데
`active_signal_duration` 이 **항상 0** 이었다. 타이머를 켜는 `set_signal_activation_time()` 이
`status_.is_valid_path` 가 참일 때만 호출되는데, 유효 경로가 없으면 `resetParameters()` 가
타이머를 지운다(한 판에 3800회). 닭-달걀이다. 결과로 prepare 가 4.0 s 에 고정돼
13.9 m/s 에서 **필요 길이 60.5 m**. 여기에 원래 횡가속(min 0.4 / max 0.65)이면 채택 후보의
중앙값이 51.5 m 라 50 m 앞 정지차 전에 기동이 끝나지 않는다.

### 4겹. 연쇄 요구
모듈은 **남은 변경 전부**가 종점 안에 들어간다는 보장이 없으면 **첫 변경도 시작하지 않는다**
(`calc_lc_length_and_dist_buffer` 가 남은 변경 전부의 길이+버퍼를 요구). 루트가 `B→A→포켓`
두 칸을 요구하는 동안 복귀가 영원히 안 됐다. seg5 를 A 로 두어 뒤따르는 변경을 없애니 즉시 성공했다.

### 5겹. 목표 차선 점유 — 이건 옳은 동작
즉시 목표 차선에 정지차가 자차의 예측 경로 안에 있으면 거부한다. 1·2차선이 동시에 막히면
어느 모듈도 이걸 뚫지 않는다. **뚫으면 안 되는 것이므로 해결 대상이 아니다.**

## 왜 avoidance 가 아니라 lane_change 인가

avoidance 로도 회피는 됐고 포켓 진입까지 완주한 판도 있다. 그러나 avoidance 는 라우팅 그래프를
보지 않아 **실선을 넘는다** — 실측으로 `15719|15750`(solid) 를 넘었고 이는 채점 항목 6(실선 차로변경)
경미 −3 이다. `lane_change` 는 실선을 넘지 않고 방향지시등도 정상 동작한다. 그래서 avoidance 를 끄고
`lane_change` 만으로 가는 구성을 택했다.

## 남은 것

- **단계 전환의 런타임화.** 지금은 하네스에서 `REROUTE` 로 손으로 넣는다. 판단 노드가
  A*(점유 반영) → 다음 한 칸만 요구 → 완료 확인 → 다음 단계로, 를 `change_route` 로 수행해야 한다.
  `is_reroute_available` 이 true 일 때만 넣는다.
- **1·2차선 동시 봉쇄**는 대기(정책). 이 경로에서는 기하적으로도 불가능하다 —
  4차선 구간 바로 앞 28 m 가 실선·단일차선(15719)이라 우회 활주로와 복귀 여유를 동시에 못 준다.
