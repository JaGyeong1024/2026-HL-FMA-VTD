## 1. 먼저 알아야 할 것 — "autoware" 라는 이름의 디렉터리가 3개다

혼동이 잦은 부분이라 먼저 정리합니다.

```
① hlfma_ws/src/autoware/          업스트림 Autoware 원본 소스 (core/universe/launcher)
                                  → .gitignore 로 제외. hlfma.repos 로 vcs import 재현
                                  → 우리 수정은 patches/*.patch 로만 보존

② hlfma_ws/src/hlfma/autoware_launch/   우리 저장소가 가진 autoware_launch 설정 사본
                                  → git 추적됨. 파라미터 작업은 전부 여기
                                  → ROS 2 overlay 우선순위상 ①보다 우선 적용된다

③ ~/autoware/                     저장소 밖의 별도 Autoware 트리. 빌드 underlay 용
                                  → 우리 작업 대상 아님
```

**왜 ②가 이기나**: `start_autonomous.sh` 는 `hlfma_ws/install/setup.bash` 를 source 하고,
그 overlay 가 `~/autoware/install` 을 underlay 로 체인합니다. 같은 이름의 패키지는 overlay 가 우선입니다.
설치본이 심볼릭 링크라 확인이 쉽습니다.

```
hlfma_ws/install/.../common.param.yaml -> hlfma_ws/src/hlfma/autoware_launch/.../common.param.yaml
   max_vel: 12.8   min_acc: -4.0     ← 실제로 적용되는 값
~/autoware/install/.../common.param.yaml -> ~/autoware/src/launcher/.../common.param.yaml
   max_vel: 13.3                     ← underlay, 가려짐
```

## 2. 커밋된 수정 — `8b2208f` (2026-09-05)

> 커밋 메시지: "회피·급출현 모듈 활성화, 정지 후 재출발 교착 해소"
> 파일 4개, 11줄 변경.

### 2-1. 플래닝 모듈 3개를 켰다

**파일**: `autoware_launch/config/planning/preset/default_preset.yaml`

```diff
- launch_static_obstacle_avoidance:        "false"
+ launch_static_obstacle_avoidance:        "true"    # 차로 내 회피 허용
- launch_avoidance_by_lane_change_module:  "false"
+ launch_avoidance_by_lane_change_module:  "true"    # 전방 막힘 시 차선변경 우회
- launch_run_out_module:                   "false"
+ launch_run_out_module:                   "true"    # 급출현 보행자 대응
```

**왜**: `개발계획_0902 §3` 은 "회피는 반대차로 침범 = 중앙선 침범 -6점을 유발한다"는 이유로
회피 모듈을 전부 꺼놨습니다. 그런데 9/3 사전 테스트에서 **갓길 정차차량 앞에 그냥 멈춰버렸습니다.**
멈추면 -3점이 아니라 **미완주**가 됩니다. 채점은 완주 그룹이 먼저이므로 전제가 뒤집혔습니다.

`run_out` 은 별개입니다. 9/3 에 도로로 뛰어드는 어린이를 못 잡았고, 9/4 검증에서
이 모듈을 끄면 충돌한다는 걸 확인했습니다.

> **주의**: `default_preset.yaml` 은 모듈의 **on/off 스위치 파일**입니다.
> 여기서 켜야 모듈이 로드되고, 그 다음에 각 모듈의 `*.param.yaml` 값이 의미를 갖습니다.
> 두 단계를 다 해야 동작이 바뀝니다.

### 2-2. 회피가 차로 밖으로 나가지 못하게 막았다

**파일**: `.../behavior_path_planner/autoware_behavior_path_static_obstacle_avoidance_module/static_obstacle_avoidance.param.yaml`

```diff
- use_lane_type: "opposite_direction_lane"
+ use_lane_type: "same_direction_lane"      # 같은 방향 차로까지만. 반대차로 금지
- use_intersection_areas:    true
+ use_intersection_areas:    false          # 교차로 여유공간 이탈 금지
- use_hatched_road_markings: true
+ use_hatched_road_markings: false          # 사선지대 침범 금지
- use_freespace_areas:       true
+ use_freespace_areas:       false          # 자유공간 이탈 금지
```

**왜**: 2-1 에서 회피를 켰으므로 이제 "회피가 중앙선을 넘는" 위험이 실재합니다.
그래서 **켜되 범위를 좁혔습니다.** 회피는 하되 같은 방향 차로 안에서만 하고,
교차로 여유공간·사선지대·자유공간으로는 나가지 않게 합니다.
즉 2-1 과 2-2 는 한 쌍입니다. 2-1 만 적용하면 -6점 위험이 그대로 남습니다.

### 2-3. 감속 한계를 -2.5 → -4.0 m/s² 로 키웠다

**파일**: `.../scenario_planning/common/common.param.yaml`

```diff
  limit:
-   min_acc: -2.5
+   min_acc: -4.0
```

**왜**: 계산으로 확정한 항목입니다. 9/4 계측에서 보행자가 **전방 30.3 m** 에 나타났고
자차 속도는 **12.68 m/s** 였습니다.

```
정지거리 = v² / (2a)
  -2.5 m/s² :  12.68² / (2 × 2.5) = 32.2 m   >  가용 30.3 m   → 물리적으로 정지 불가
  -4.0 m/s² :  12.68² / (2 × 4.0) = 20.1 m   <  가용 30.3 m   → 여유 10 m
```

VTD 제어 패킷의 감속 한계는 -6.0 m/s² 이므로 -4.0 은 아직 여유가 있습니다.
**즉 이건 "더 잘 서게 하는" 튜닝이 아니라, 원래 설정으로는 서는 게 불가능했던 걸 고친 겁니다.**

### 2-4. 정지 후 재출발 교착을 풀었다

**파일**: `.../common/autoware_velocity_smoother/velocity_smoother.param.yaml`

```diff
- engage_velocity:     0.25
+ engage_velocity:     0.5
- engage_acceleration: 0.5
+ engage_acceleration: 1.0
- engage_exit_ratio:   0.5
+ engage_exit_ratio:   0.1
```

**왜**: 신호 대기 후 재출발할 때 차가 **0.2 km/h 로 기어가며 안 나가는** 현상이 있었습니다.
초록불 30 m 앞에서 20초 넘게 크립하면 채점 8번 항목 -6점입니다.

실주행 계측으로 원인을 특정했습니다.

```
궤적 속도가 engage_velocity(0.25 m/s)에 73초간 고정
실제 속도는 0.063 ~ 0.077 m/s
engage 시퀀스 탈출 문턱 = engage_velocity × engage_exit_ratio = 0.25 × 0.5 = 0.125 m/s
→ 실속도가 문턱을 영영 못 넘어 engage 시퀀스를 빠져나오지 못함 (자기잠금)
```

문턱을 `0.5 × 0.1 = 0.05 m/s` 로 낮춰 해소했습니다.
**이 항목은 실주행에서 재출발 정상 동작을 직접 확인했습니다.** 커밋된 4건 중 유일하게 실증된 항목입니다.

### 3-2. `external_request_lane_change_non_preferred.patch` (2026-09-06)

- **대상**: `autoware_behavior_path_lane_change_module` 의 `get_target_neighbor_lanes`
- **증상**: 전방이 막혔는데 우측 차선변경 후보가 **하나도 생성되지 않음**.
  로그에 `lane_change.EXTERNAL_REQUEST: lanes are not available` 경고.
- **원인**: 기존 함수는 자차가 **우선 차로(preferred lane)가 아닌 곳**에 있으면 자차 차로를 후보에서 제외합니다.

  좌회전 대기줄에서 벗어나 우회하려는 상황이 정확히 이 조건에 걸립니다.

- **회귀 테스트 동봉**: `test_lane_change_scene.cpp` 에

- **적용**:

## 4. 우리가 만든 ROS 노드 — `vtd_autoware_bridge`

Autoware 설정만이 아니라 **우리 코드도 있습니다.** yaml 만 커밋하면 이게 빠집니다.

| 파일 | 역할 |
|---|---|
| `bridge_node.py` | VTD ↔ Autoware 변환의 본체. 패킷 파싱(1109B @20Hz), ego pose, 인지 객체 변환, 신호등 발행, 제어 명령 송신(9B) |
| `route_node.py` | 경로 주입. CSV 좌표열 → lanelet 매칭 → ADAPI `set_route_points` |
| `osm_map.py` | lanelet2 맵 로드·투영·최근접 매칭 |
| `protocol.py` | VTD 패킷 구조 정의 |
| `tl_router.py` | 신호등 상태 → 다음 정지선 규제요소 라우팅 |
| `blocked_route_detour.py` | **신규(9/6)** — 정지 차량군 우회 RTC 승인 게이트 |

### `blocked_route_detour.py` (209줄, 미커밋)

```
Autoware가 좌/우 후보와 안전성 검사를 만들고, 이 노드는 ego가 실제로 정지 차량에
막히기 전 접근 중에 후보 path의 빈 corridor가 더 긴 방향만 ACTIVATE한다.
조향/정지 제어는 하지 않는다.
```

**설계 의도가 중요합니다.** 이 노드는 **경로를 만들지 않습니다.** 후보 생성·안전성 검사는
전부 Autoware 가 하고, 이 노드는 **어느 쪽을 승인할지만 고릅니다.**
"막히면 무조건 우측" 같은 하드코딩을 피하기 위한 구조입니다 — 실제 대회 시나리오를 모르기 때문입니다.

같이 들어간 배선 변경:

```diff
# bridge.launch.xml — 노드 등록
+ <node pkg="vtd_autoware_bridge" exec="blocked_route_detour" name="blocked_route_detour">
+   <param name="map_osm" value="$(var map_osm)"/>
+ </node>

# package.xml — RTC 메시지 의존성
+ <depend>autoware_internal_planning_msgs</depend>
+ <depend>tier4_rtc_msgs</depend>

# setup.py — 실행 진입점
+ 'blocked_route_detour = vtd_autoware_bridge.blocked_route_detour:main',
```

## 6. 코드는 안 고쳤지만 반드시 알아야 할 함정 — RTC 자동 승인

9/6 에 확인한 내용입니다. **설정 변경은 없지만, 모르면 몇 시간을 날립니다.**

`autoware_rtc_interface/src/rtc_interface.cpp`:

```cpp
void RTCInterface::updateCooperateCommandStatus(const std::vector<CooperateCommand> & commands) {
      itr->command_status = command.command;
      itr->auto_mode = false;        // ← 수동 명령이 오면 그 UUID 의 자동승인을 끈다
}

bool RTCInterface::isActivated(const UUID & uuid) const {
  if (itr->auto_mode && !itr->requested) return itr->safe;   // 자동승인 경로
  return itr->command_status.type == Command::ACTIVATE;      // 수동 경로
}
```

lane_change 계열은 `requested` 가 항상 false 입니다
(`interface.hpp` 의 4인자 오버로드에서 3번째 인자는 `safe`, `updateCooperateStatus` 의 `requested` 는 기본값 false).

**따라서 자동 승인이 켜져 있으면 `isActivated` 는 `safe` 값을 그대로 반환합니다 — 명령이 필요 없습니다.**

여기서 함정: **승인을 재촉하려고 ACTIVATE 를 보내면 오히려 승인이 막힙니다.**
명령이 도착하는 순간 그 UUID 의 `auto_mode` 가 false 로 강등되어 수동 경로로 떨어지고,
후보 경로가 재계산되어 UUID 가 바뀌면 이전 명령이 승계되지 않습니다.

실주행 확인 결과:

```
수동 ACTIVATE 를 보낼 때:  (safe=True, cmd=0) 인데 승인 안 됨 → cmd=1 도착 시점엔 이미 시작점 통과
수동 ACTIVATE 를 안 보낼 때: am=True, auto_mode=True, safe=True, state=1(RUNNING), cmd=0
                            → 명령 없이 승인·실행 상태 진입
```

**정리**: `enable_rtc: false` 인 모듈에는 절대 수동 명령을 보내지 마세요.
`blocked_route_detour` 가 승인을 보내야 하는 external-request 모듈만
`enable_rtc: true` 로 둔 이유가 이것입니다(5-2).

## 8. 미해결 — 좌회전 정체 구간 우회

가장 오래 남아 있는 과제입니다. 상세 기록은 `문서보관/검토보고_0905_정체차로_교착.md` 에 있습니다.

**상황**: 좌회전해야 하는데 좌회전 차로가 사고로 막혀 있음. 자차 차로에도 정지차가 있음.

**확인된 구조**:
1. 자차 차로가 전방 약 10.9 m 에서 막힘
2. 좌회전 차로도 정지차로 막힘
3. 우측 차로는 비어 있으나, 경로의 preferred 가 좌회전 차로라 우측으로 갈 동기가 없음

**진행 상황**:
- 관측 기반 재라우팅(정지차 수를 세어 빈 차로로 preferred 교체)은 end-to-end 로 동작 확인
- RTC 승인 경합 해결(6장) — 차선변경 모듈이 RUNNING 상태 진입 확인
- 그러나 `obstacle_stop` 이 자차 위치에 정지점을 삽입해, 차선변경 prepare 구간(약 7 m)조차 진행 못 함
  ```
  /planning/planning_factors/obstacle_stop
    control_points[0].distance: -0.097     ← 정지점이 자차 바로 위
  ```
- 차선변경 전체 소요 약 65 m 대비 가용 구간은 약 15 m. **거리 부족이 실재**
  (`utils.cpp:330` 확인 — RTC 의 `finish_distance` 는 shift line 종료점까지의 실제 호 길이가 맞음)
- 3-2 패치 + `blocked_route_detour` 조합이 이 문제의 현재 접근입니다

**하드코딩 금지 원칙**: 실제 대회 시나리오를 모르므로
"처음부터 우측으로 간다", "막히면 무조건 오른쪽" 같은 규칙은 쓰지 않습니다.
관측(정지 객체 분포)으로 판단하는 일반해만 씁니다.

## 9. 클린 체크아웃에서 되살리는 방법

```bash
git clone git@github.com:JaGyeong1024/2026-HL-FMA-VTD.git
cd 2026-HL-FMA-VTD

# 1. 업스트림 Autoware 소스 가져오기 (gitignore 대상이라 별도)
cd hlfma_ws && vcs import src < hlfma.repos && cd ..

# 2. 업스트림 패치 재적용 — 빠뜨리면 set_route 가 hang 한다
patch -p0 < patches/route_handler_getMainLanelets_guard.patch
patch -p1 < patches/external_request_lane_change_non_preferred.patch

# 3. acados(MPC) 런타임 등록
echo /opt/acados/lib | sudo tee /etc/ld.so.conf.d/acados.conf && sudo ldconfig

# 4. 빌드 — 반드시 hlfma_ws 안에서
cd hlfma_ws && colcon build --symlink-install

# 5. 실행
cd .. && ./start_autonomous.sh      # 브리지 + Autoware 기동
         ./start_hlfma.sh            # engage
```

> **자주 하는 실수**: 저장소 루트에서 `colcon build` 하면 `build/ install/ log/` 가 루트에 생깁니다.
> 반드시 `hlfma_ws/` 안에서 실행하세요.
